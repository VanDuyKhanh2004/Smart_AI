## [Unreleased]

> **Historical note (2026-08-04):** The centralized error-handling migration described incrementally below (Phases 1–3) is now **complete** — all 18 controllers use `asyncHandler` + `AppError`. Earlier entries that describe intermediate states (e.g., "createOrder remains legacy (Phase 3)") are historical snapshots of prior PRs and no longer describe the current code. The legacy `{ success, message }` error envelope remains only on product create/update and the store, appointment, profile, and address route groups.

### Added
- Lightweight product metadata endpoint `GET /api/products/meta` (`controllers/productController.js`) — returns normalized, unique, alphabetically-sorted active brand list via `Product.distinct`; no product documents, specs, or review lookups; dedicated `product-meta` Redis cache key (TTL 300s, malformed/shape-invalid cache falls back to Mongo); cache write failures never break the read response; invalidated on product create/update/delete alongside `products:*`
- Per-user chat conversation ownership (`models/Conversation.js`) — `userId` (ObjectId ref to `User`) stored with each conversation; ownership enforced by the logical pair `{ userId, sessionId }` via a unique compound index; global `sessionId` uniqueness removed so two users can each own the same client-visible `sessionId`
- Non-breaking ownership contract docs — see **Changed** for the migration/legacy policy and Redis key isolation notes
- `tests/chatConversationOwnership.test.js` (18 scenarios: authenticated user stored on new conversations, compound lookup `{ sessionId, userId }`, same-user resume, cross-user isolation with a shared `sessionId`, foreign-user append blocked, foreign history never included in the LLM prompt, client-supplied payload `userId` ignored, missing authenticated user rejected, legacy unowned conversation not auto-claimed, per-user Redis context keys, two users + same `sessionId` → separate Redis context, complaint flow scoped by owned conversation)
- MongoDB index migration `scripts/migrateConversationOwnershipIndex.js` — safely swaps the legacy globally-unique `sessionId_1` index for the ownership-pair unique index `userId_1_sessionId_1` (`{ userId: 1, sessionId: 1 }`): dry-run capable, idempotent, orders the change (create target unique → verify → drop legacy → verify final), aborts with no index change if duplicate `{ userId, sessionId }` pairs exist or if the target index is not unique, reports (but never writes) legacy documents without a `userId`, and exits non-zero on any real failure
- `npm run migrate:conversation-ownership-index` (live) and `npm run migrate:conversation-ownership-index:dry-run` (report-only) follow the existing `migrate:product-images*` naming pattern (`Smart_AI_backend/package.json`)
- `tests/migrateConversationOwnershipIndex.test.js` (19 scenarios: pure planner for legacy-only / drop-only / already-migrated / duplicate-block / non-unique-block; orchestration for create→verify→drop ordering, dry-run no-op, duplicate abort pre-change, legacy docs reported but documents untouched, create/verify/drop/final-verify failures, clean connect/disconnect exit codes)
- Chat message correlation / duplicate-processing guard service `Smart_AI_backend/services/chatMessageDedupService.js` — claims a submission with Redis `SET NX EX` on key `chat:message:user:<userId>:<sessionId>:<clientMessageId>` (JSON `{ state: 'processing' }`, TTL `CHAT_MESSAGE_DEDUP_TTL_SECONDS` default 1800s); duplicate delivery returns `{ claimed:false, duplicate, status, payload }`; `markCompleted()` stores `{ state:'completed', payload }` for same-id replay; `release()` clears a claim on failure so an explicit retry can reprocess; bounded process-local LRU fallback (max `CHAT_MESSAGE_DEDUP_LOCAL_MAX` default 1000, TTL sweep + eviction) when Redis is unavailable; message content never appears in keys, values, or logs
- Chat message correlation (backend tests): `tests/chatMessageDedupService.test.js` (9 scenarios: claim once, duplicate-while-processing, completed replay, release reprocess, revivePayload copy, expired reclaim, bounded local store, key scoping), `tests/chatMessageCorrelation.test.js` (9 scenarios: `aiResponse` carries id across product/small-talk/complaint, user+assistant persist the id, defensive duplicate-user/assistant guards, single terminal error, `buildAiPayload` shape), `tests/chatSocketCorrelation.test.js` (9 scenarios: real in-memory Socket.IO ack lifecycle, `messageProcessing` correlation, duplicate suppression + replay, in-flight dedup, malformed-id rejection, legacy no-id path, single correlated `error` + `error` ack, released-claim resend, cross-session distinctness)
- Chat message correlation (frontend) `src/tests/ChatServiceCorrelation.test.ts` (8 scenarios: duplicate local submit → one bubble + one emit, ack releases pending slot, in-flight dedup, one render per `clientMessageId`, distinct ids render separately, error ack frees slot, disconnect frees pending, reset-session clears correlation state)
- Streaming chat responses: provider deltas are emitted progressively to the client
  - `generateChatResponseStream()` (`Smart_AI_backend/utils/gemini.js`) — same OpenAI-compatible → Gemini → deterministic fallback chain as `generateChatResponse`, but yields deltas via `onDelta`, caps assembled output at `MAX_STREAMED_TEXT_CHARS` (env `MAX_CHAT_RESPONSE_CHARS`, default 4000) with `finishReason: 'max_tokens'`, and preserves partial output on a mid-stream failure via `error.partialContent`; the deterministic fallback returns `streamed: false` (intentionally buffered — no deltas emitted)
  - `streamOpenAICompatible()` / `streamGeminiChat()` streaming helpers using `chat.completions.create({ stream: true })` and `models.generateContentStream` respectively, both respecting an optional abort `signal`
  - New socket events for a **live streamed success**: `aiResponseStart` (exactly once, before the first chunk), `aiResponseChunk` `{ sessionId, clientMessageId, chunk, chunkIndex, timestamp }` (each `chunk` is a DELTA to be appended, batched by `createChatStreamBatching` (`Smart_AI_backend/services/chatStreamBatching.js`, ≈40 chars / ≈40 ms flush); `chunkIndex` is mandatory and zero-based sequential, empty chunks never emitted), and `aiResponseComplete` `{ sessionId, clientMessageId, content, finishReason, totalChunks, timestamp, metadata? }` (exactly once, the authoritative content that is displayed and persisted). **No `aiResponse` is emitted for a live streamed success.**
  - `aiResponse` is now reserved for exactly two paths: (1) an **intentionally buffered** fallback (deterministic, small talk, complaint) and (2) **completed duplicate replays**. It is never emitted for a live stream.
  - `ChatController.generateResponse` (`Smart_AI_backend/controllers/chatController.js`) — uses streaming when available, reads `streamed` from the stream result to choose `aiResponseComplete` (live) vs `aiResponse` (buffered), falls back to the classic single-shot path when the module under test lacks the streaming export, and propagates a mid-stream failure (no terminal complete, no fallback after any emitted chunk) to the socket boundary for a single correlated error
  - Frontend `chat.service.ts` — the one-placeholder lifecycle: `aiResponseStart` creates the single assistant placeholder `stream:<clientMessageId>`, each `aiResponseChunk` appends a delta into that same message (sequential `chunkIndex` only; stale/duplicate/out-of-order rejected), `aiResponseComplete` finalizes it with the authoritative content; a stray/replayed `aiResponse` for an already-delivered id is ignored (`deliveredStreamIds`); a `aiResponse` without a prior stream (buffered/replay) still renders once; correlated `error` marks/removes the placeholder via `onStreamError`
  - `FloatingChat`/`ChatMessage` — one assistant bubble per `clientMessageId`: `onStreamStart` drops the generic loading bubble and creates the placeholder, `onMessageUpdate` fills it, `onStreamComplete` finalizes it, `onStreamError` marks it failed; loading indicator removed at `aiResponseStart`
  - Backend tests `tests/chatStreamFallback.test.js` (OpenAI streaming, Gemini fallback, buffered deterministic fallback, partial-content preservation, no-fallback-after-chunk, output ceiling → `max_tokens`), `tests/chatStreamBatching.test.js` (threshold/timer flush, delta-only chunks, no empty chunks, residual flush, chunk indexes, dispose cleanup), and `tests/chatStreamController.test.js` (the streaming event contract: exactly-once start/complete, delta-only zero-based sequential `chunkIndex`, no empty chunks, authoritative complete `+ totalChunks`, no `aiResponse` on live success, buffered-fallback `aiResponse`, propagation of failures before/after a chunk)
  - Frontend tests `src/tests/ChatServiceStreaming.test.ts` (the one-placeholder lifecycle: start creates one assistant message, deltas mutate the same message, complete finalizes with authoritative content replacing local, `chunkIndex` sequence enforced, stale/duplicate/out-of-order/empty/foreign ignored, stray `aiResponse` for a delivered id ignored, buffered `aiResponse` still rendered, concurrent streams isolated, correlated-error cleanup, reset/disconnect clearing, markdown preserved)

### Changed
- Chat conversation lookups now require both `sessionId` and the trusted authenticated `userId` (`controllers/chatController.js`) — every find/create of the conversation, history load, user-message save, assistant-response save, and complaint persistence is scoped by ownership; a client-supplied `sessionId` can no longer resolve another user's conversation
- Trusted identity source — the controller reads `userId` exclusively from `socket.data.user.id` (set by the socket auth middleware); any `userId` sent in the client payload is ignored (`controllers/chatController.js`)
- Redis context isolation — context keys now include the trusted user: `chat:context:user:<userId>:<sessionId>` for authenticated callers (`services/contextService.js`); legacy anonymous `chat:context:anon:<sessionId>` keys are never read by authenticated flows after this fix; TTL unchanged; Redis-unavailable remains non-fatal
- Chat logging — `controllers/chatController.js` and `services/contextService.js` now use the project logger instead of `console.*`
- Product metadata route registered before `/:id` (`routes/productRoutes.js`) so `/api/products/meta` is never treated as a product ID lookup; documented in Swagger (`configs/swagger.js`) and synced into `tests/route-accuracy.test.js` routeMap
- `tests/productMeta.test.js` (25 tests: normalization, dedupe, sorting, inactive exclusion, empty collection, cache hit/miss, malformed cache fallback, Redis-unavailable fallback, write-path invalidation, route ordering, semantic/list routes unaffected, no console logging)
