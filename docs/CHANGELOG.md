## [Unreleased]

> **Historical note (2026-08-04):** The centralized error-handling migration described incrementally below (Phases 1–3) is now **complete** — all 18 controllers use `asyncHandler` + `AppError`. ### Added
- Retry and Regenerate AI response (`feat/chat-retry-regenerate`):
  - Two identities introduced and documented: `clientMessageId` = the **logical turn**, `generationId` = the **attempt**. Ordinary `sendMessage` defaults `generationId` to `clientMessageId`; Retry re-uses it; Regenerate mints a **fresh** `generationId` at the socket boundary (backward compatible — stream events carry `generationId` only when it differs from `clientMessageId`).
  - Schema (`models/Conversation.js`): optional `generationId` on message subdocs (String, trimmed, **no index**, additive/legacy-compatible — no migration). Helper resolvers `getUserMessageByClientMessageId` / `getAssistantMessageByClientMessageId` (logical-turn lookup).
  - `services/chatActiveStreams.js`: generation-aware identity keying plus a **logical-turn guard** (`claimLogical` / `releaseLogical` / `isLogicalActive`) that closes the regenerate double-click window even though every click mints a fresh attempt id.
  - `controllers/chatController.js` (module still exports a singleton `new ChatController()`): shared `renderResponse` pipeline extracted from `processMessage`, `verifyRetryTarget`, `verifyRegenerateTarget`, `retryMessage`, `regenerateMessage`, `replaceAIResponse` (**generate-then-atomic-replace**, old assistant untouched until the new generation succeeds), `saveAIResponse` stamps `generationId`; `processMessage` / retry / regenerate pass `persistContext` so only a genuinely new logical turn advances context/`turnCount`.
  - `socket/socketHandler.js`: explicit `retryMessage` / `regenerateMessage` events. Retry ack `{ accepted, duplicate, status, clientMessageId, generationId }`, status ∈ `accepted|already_processing|already_completed|not_found|invalid|error` (server loads the original user content; no text sent). Regenerate ack `{ accepted, status, clientMessageId, generationId }`, status ∈ `accepted|already_processing|not_completed|not_found|invalid|error` with the fresh `generationId` on accept. Regenerate claims its own dedup slot (`userId+sessionId+generationId`), reuses the logical turn for persistence, and releases/cleans up active + logical guard on success/cancel/error.
  - `utils/chatCancellation.js`: `isCancellationError` exported (shared cancellation identity reused across Retry/Regenerate; no partial assistant ever persisted).
  - Frontend `src/services/chat.service.ts`: `generationId`/`regenerating` on `ChatMessage`; `RetryAck`/`RegenerateAck` types; `retryMessage(clientMessageId)`, `regenerateMessage(clientMessageId, previousContent)`, `stopGenerationAttempt(attemptId)`; regenerate bookkeeping maps (by fresh `generationId`) and callbacks (`onRegenerateAccepted/Started/Update/Complete/Failed/Cancelled`); streaming / `messageProcessing` / `error` routing keyed by attempt `generationId` when present, otherwise the logical id; cleanup on disconnect/reset-session.

- Streaming chat responses: provider deltas are emitted progressively to the client
  - `generateChatResponseStream()` (`Smart_AI_backend/utils/gemini.js`) — same OpenAI-compatible → Gemini → deterministic fallback chain as `generateChatResponse`, but yields deltas via `onDelta`, caps assembled output at `MAX_STREAMED_TEXT_CHARS` (env `MAX_CHAT_RESPONSE_CHARS`, default 4000) with `finishReason: 'max_tokens'`, and preserves partial output on a mid-stream failure via `error.partialContent`; the deterministic fallback returns `streamed: false` (intentionally buffered — no deltas emitted)
  - `streamOpenAICompatible()` / `streamGeminiChat()` streaming helpers using `chat.completions.create({ stream: true })` and `models.generateContentStream` respectively, both respecting an optional abort `signal`
  - New socket events for a **live streamed success**: `aiResponseStart` (exactly once, before the first chunk), `aiResponseChunk` `{ sessionId, clientMessageId, chunk, chunkIndex, timestamp }` (each `chunk` is a DELTA to be appended, batched by `createChatStreamBatching` (`Smart_AI_backend/services/chatStreamBatching.js`, ≈40 chars / ≈40 ms flush); `chunkIndex` is mandatory and zero-based sequential, empty chunks never emitted), and `aiResponseComplete` `{ sessionId, clientMessageId, content, finishReason, totalChunks, timestamp, metadata? }` (exactly once, the authoritative content that is displayed and persisted). **No `aiResponse` is emitted for a live streamed success.**
  - `aiResponse` is now reserved for exactly two paths: (1) an **intentionally buffered** fallback (deterministic, small talk, complaint) and (2) **completed duplicate replays**. It is never emitted for a live stream.
  - `ChatController.generateResponse` (`Smart_AI_backend/controllers/chatController.js`) — uses streaming when available, reads `streamed` from the stream result to choose `aiResponseComplete` (live) vs `aiResponse` (buffered), falls back to the classic single-shot path when the module under test lacks the streaming export, and propagates a mid-stream failure (no terminal complete, no fallback after any emitted chunk) to the socket boundary for a single correlated error
  - Frontend `chat.service.ts` — the one-placeholder lifecycle: `aiResponseStart` creates the single assistant placeholder `stream:<clientMessageId>`, each `aiResponseChunk` appends a delta into that same message (sequential `chunkIndex` only; stale/duplicate/out-of-order rejected), `aiResponseComplete` finalizes it with the authoritative content; a stray/replayed `aiResponse` for an already-delivered id is ignored (`deliveredStreamIds`); a `aiResponse` without a prior stream (buffered/replay) still renders once; correlated `error` marks/removes the placeholder via `onStreamError`
  - `FloatingChat`/`ChatMessage` — one assistant bubble per `clientMessageId`: `onStreamStart` drops the generic loading bubble and creates the placeholder, `onMessageUpdate` fills it, `onStreamComplete` finalizes it, `onStreamError` marks it failed; loading indicator removed at `aiResponseStart`

  - Frontend tests `src/tests/ChatServiceStreaming.test.ts` (the one-placeholder lifecycle: start creates one assistant message, deltas mutate the same message, complete finalizes with authoritative content replacing local, `chunkIndex` sequence enforced, stale/duplicate/out-of-order/empty/foreign ignored, stray `aiResponse` for a delivered id ignored, buffered `aiResponse` still rendered, concurrent streams isolated, correlated-error cleanup, reset/disconnect clearing, markdown preserved)
- Stop AI generation (`feat/chat-stop-generation`):
  - `Smart_AI_backend/services/chatActiveStreams.js` — process-local registry of live streams keyed by `userId:sessionId:clientMessageId` with `register`/`get`/`abort` (aborts the controller exactly once and removes the entry)/`markCompleted`/`remove`/`removeForSocket`/`isCompleted`, plus TTL sweeps (`CHAT_STREAM_TTL_MS`, `CHAT_COMPLETED_TTL_MS`, completed set capped by `CHAT_COMPLETED_MAX`). Single-instance only by design.
  - `ChatController.generateResponse` creates one `AbortController` per live stream, registers it, and threads `controller.signal` into `generateChatResponseStream`; `markCompleted` on normal finish, `remove` on failure/cancel. The abort check right after the provider resolves prevents an abort/complete race.
  - Provider abort identity (`utils/gemini.js`) — `throwIfAborted` and the orchestrator's final catch both normalize to the shared error `{ cancelled: true, code: 'STREAM_CANCELLED' }`, so the socket boundary distinguishes user cancellation from a genuine failure (`streamOpenAICompatible` passes the signal to `create({ stream: true, signal })`; Gemini checks between yields).
  - Socket `stopGeneration` event (`socket/socketHandler.js`) — ack `{ stopped, status: 'stopped'|'already_completed'|'not_found'|'invalid', clientMessageId }` (exactly once); abort → the running pipeline rejects with `STREAM_CANCELLED` and the boundary emits the **single terminal** `messageProcessing { status: 'cancelled', reason: 'user_cancelled' }` — never the generic `error`, never `aiResponseComplete`, never a new `aiResponseCancelled` event. The dedup claim is released so the same id reprocesses as fresh. `disconnect` sweeps (aborts) the socket's live streams.
  - No partial assistant content is ever persisted for a cancelled stream.
  - Frontend `chat.service.ts` — `stopGeneration(clientMessageId)` (emits only for a real live stream; returns `false` otherwise), `isLiveStreaming()` getter, and the `messageProcessing 'cancelled'` handler (finalizes the placeholder, keeps partial content, calls `onStreamCancelled`; a late complete / stale duplicate cancelled is ignored). `FloatingChat` tracks the active stream id; `ChatWindow` replaces Send with a Stop button while a live stream is active; `ChatMessage` shows a "Đã dừng" badge on a cancelled bubble.

  - Backend tests: `tests/chatActiveStreams.test.js` (11), `tests/chatStopGeneration.test.js` (12, real in-memory Socket.IO), `tests/chatGenerationCancel.test.js` (6, controller abort plumbing + provider identity).
  - Frontend tests: `src/tests/ChatServiceStop.test.ts` (8).

- Stop AI generation — full-lifecycle cancellation (refactor of `feat/chat-stop-generation`):
  - **One AbortController per accepted request**, created at the socket boundary (`socket/socketHandler.js`) **after** auth/validation/dedup-claim and **before** `messageProcessing 'started'` / `processMessage`, registered into `chatActiveStreams`. `generateResponse` no longer creates or registers a controller — there is exactly one registration per request, and the abort `signal` is threaded through `processMessage → intent → context → RAG → generateResponse → generateChatResponseStream → streamOpenAICompatible/streamGeminiChat`.
  - The generation is cancellable from its very first processing instant, **not** gated on `aiResponseStart` — so Stop is available during the thinking/intent/RAG phase and for buffered/deterministic branches, which never emit `aiResponseStart`.
  - Shared cancellation identity `utils/chatCancellation.js` — one helper `throwIfCancelled(signal)` producing `{ aborted: true, cancelled: true, code: 'STREAM_CANCELLED' }`, used by the provider wrappers, the orchestrator, the controller checkpoints, and the socket boundary. A cancellation is never logged with `logger.error`.
  - `processMessage` asserts checkpoints between/before phases (before work, after `manageSession`, after intent, before/after context, before/after RAG, before provider, before completion, before assistant persistence, before dedup mark) so an abort halts every later phase — no RAG/provider/fallback begins after a stop and no flush after a cancel. A stop landing as `processMessage` resolves is treated as cancelled (checkpoint before the `completed` emit and before the dedup completion mark).
  - `chatActiveStreams` lifecycle now represents **active generations**: `register` (boundary) → success `markCompleted` / cancel `abort`+remove / genuine error `remove` / disconnect `removeForSocket`. **An expired active entry aborts its controller before being deleted** (so an orphaned in-flight call cannot run to completion); a re-register aborts any superseded live entry.
  - Frontend `chat.service.ts` now tracks `cancellableGenerationIds` (populated from `messageProcessing 'started'`, cleared by `completed`/`cancelled`/`error`/compatibility `aiResponse`/`disconnect`) with `isActiveGeneration()`/`getActiveGenerationId()`; `stopGeneration(clientMessageId)` works for any cancellable id including one with no stream placeholder yet. `FloatingChat` shows the Stop control for the whole processing window; the old `isLiveStreaming`-only Stop is gone. No artificial slowdown — a fast/deterministic finish clears Stop naturally.
  - Optional dev/test-only `CHAT_STREAM_TEST_DELAY_MS` (default 0/disabled) to hold a phase for manual verification of the Stop control.
  - Backend tests: `tests/chatStopGeneration.test.js` expanded (single controller at boundary, `started`→signal threading, two concurrent ids isolated, genuine-error cleanup), `tests/chatGenerationCancel.test.js` rewritten to the caller-provided `signal` contract, `tests/chatCancellationCheckpoints.test.js` (new: pre-abort cancels before any work; cancel during intent prevents RAG/provider/save; user message persists but assistant never saved; normal run completes + saves), `tests/chatActiveStreams.test.js` (new stale-ABORT sweep case).
  - Frontend tests: `src/tests/ChatServiceStop.test.ts` (19 now).
  - Docs: `docs/CHAT_MESSAGE_CORRELATION.md` §10 rewritten (boundary controller, threading, checkpoint list, races, frontend Stop window, `CHAT_STREAM_TEST_DELAY_MS`); `CHANGELOG.md` (this entry).
